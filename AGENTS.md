## Start here

**Read the documentation and inspect existing implementation before changing code.** Start with [README](README.md), [Architecture](ARCHITECTURE.md), [TRD](TRD.md), and [Phases](Phases.md). Check `git status` first and preserve pre-existing user/agent changes. Source and tests outrank old documentation.

## Architecture and module boundaries

- CLI orchestration: `nsat/cli/`; core discovery/config/surface/orchestration: `nsat/core/`.
- Analyzer adapters: `nsat/analyzers/`; scanners: `nsat/scanners/`.
- Canonical findings: `nsat/normalization/`; optional validation: `nsat/swarm/`; oversight: `nsat/oversight/`.
- Correlation/risk: `nsat/correlation/`; model integration/context: `nsat/ai/`.
- Remediation safeguards: `nsat/remediation/`; audit exporters: `nsat/reporting/`; PDF artifact: `nsat/remediation_report/`.
- Regression suites: `tests/`.

Do not assume an available scanner module is called by the Phase 2 orchestrator or that a registered CLI command has working behavior. `host`, `network`, and `monitor` are placeholders in this checkout. `sarif`/`html` are accepted report format choices but lack actual renderer support.

## Coding expectations

- Make the smallest coherent change; avoid unnecessary refactoring.
- Preserve public model and CLI behavior unless the task explicitly changes it.
- Keep deterministic findings separate from model-generated explanations.
- Use typed models and focused helpers consistent with neighboring modules.
- Validate filesystem paths against the target root; do not follow unsafe paths from model output.
- Do not add dependencies or external integrations without necessity and documented installation support.

## Analyzer and scanner conventions

Analyzer additions should implement the current `LanguageAnalyzer` interface, return structural/evidence-backed project indicators, register in `get_default_analyzers()`, and state coverage boundaries. Primary MVP adapters: C++, Python, Rust, Go, PHP, JavaScript, TypeScript; Java remains additional compatibility support.

Scanner changes should emit `CanonicalFinding` with evidence and provenance, use stable signature/deduplication behavior where appropriate, and handle malformed inputs safely. Add to `Phase2Orchestrator` explicitly if the scanner is part of default audit. Active checks must use existing target-scope and bounded request safeguards.

## Tests and documentation

Follow existing phase test organization. Add targeted cases for the changed code, including malformed inputs, failures, and safety constraints. Do not claim test success unless actually run. Update README/PRD/TRD/architecture/setup/phase docs when behavior changes; keep commands, language lists, models, and report capabilities synchronized with source.

## AI and security constraints

Follow [AI_INSTRUCTION.md](AI_INSTRUCTION.md): deterministic source of truth, evidence-first reasoning, distinguish observed/inferred/recommended, minimize and redact context, handle uncertainty, and treat patches as untrusted proposals. Redaction is pattern-based and incomplete by nature.

Never add unauthorized scanning, destructive probing, denial of service, exploit generation, credential exfiltration, or hidden persistence. Do not place secrets or sensitive user data in logs, fixtures, reports, or commits. Never send messages to external parties on a user’s behalf unless explicitly authorized.

## Safe development

- Never reset, checkout, revert, or delete unrelated work to simplify a task.
- Inspect status/diff before edits; keep generated bytecode, reports, `.env`, and local audit context out of commits.
- A remediation backup/hash mismatch is a conflict. Preserve newer user changes; do not force overwrite as a shortcut.
- Avoid running destructive commands against a real project. Use repository fixtures or disposable targets.
- Review generated PDFs and reports for sensitive paths and secrets before sharing.

## Errors and change scope

Surface actionable errors without dumping credentials or source secrets. Partial scan behavior must be clear; a failed scanner is not equivalent to a clean result. Do not introduce broad catches that conceal safety failures. Do not modify unrelated modules, tests, generated files, or implementation behavior when the task is documentation-only.
